**Главное честное резюме:**
1. **По визуалу и каталогу конкуренты вас пока сильно обгоняют** — не из-за лучшего кода, а из-за того, что их пайплайн рендерит **уникальный HTML** (toi) или **уникальные 50-слойные макеты** (shaqyru24) на каждый шаблон, а вы рендерите **один набор React-секций** с разными theme/asset-переменными. Это архитектурный компромисс.
2. **По бэкенду/функциональности гостей, оплаты, безопасности вы их обгоняете** — и это не «нам кажется», это видно по модели данных и интеграциям (Kaspi API vs ручная проверка скриншотов у toi; персональные токены; расадка; ресторанные линки; агентский тариф).
3. **По редактору** вы выбрали золотую середину, но она ещё не «допилена» визуально — архитектура документа и live-превью такая же или более солидная, чем у toi, но UX/визуал отстаёт.
4. **По способу создания шаблонов — у вас самая «инженерная» модель, но самая медленная в плане выхода количества и вау-эффекта.** Подробно — ниже.

## 1. Как устроены сами пригласительные — детальный разбор

### 1.1 shaqyru24.kz — движок Tyrasoft (white-label canvas)

**Инженерная суть:** это не сервис пригласительных, это **продукт Tyrasoft** (`tyrasoft.kz` — казахстанская web-студия, которая делает сайты-билдеры для тоев). Пригласительное — это страница site-builder'а с:

```
builderPageData.blocks[0]   // один большой <div> на 5700+ px
└── components[]   // 50–55 карточек: { type, position:{x,y,z}, size, style, data }
```

Типы компонентов (из реверс-инжиниринга демо `c196b73b` и `5b78d64a` в `scripts/shaqyru24_v2_inventory.md`):

| type | штук | что это |
|---|---|---|
| image | 17 | декор: рамки, углы, розы, фоны, орнаменты, confetti — **isPhoto:false** (т.е. не фото пользователя, а декор студии) |
| lottie | 8 | Lottie-анимации (открытие конверта, свечение, лепестки) |
| text | 12 | живые HTML `<p>/<h1>` слои с абсолютным позиционированием. Именно это пользователь правит через quick-edit |
| shape | 8 | геометрические фигуры (линии, круги, карточки) |
| video | 1 | фоновое hero-видео |
| audio-fixed | 1 | MP3-плеер |
| calendar | 1 | кастомный виджет (сердце-маркер, казахские названия дней/месяцев, KZPFMonumentaPro) |
| timer | 1 | обратный отсчёт (days/hours/minutes/seconds) с timezone Asia/Almaty |
| button | 1 | «Картаны ашу» → 2GIS |
| form2 | 1 | RSVP с одним полем «Есіміңіз» |
| fixed-wishes | 1 | кнопка «ТІЛЕК ЖАЗУ» |
| wishes-list | 1 | автопрокручиваемая стена пожеланий |

**Шрифты Tyrasoft** — это не Google Fonts, это **лицензионные KZ-серии**:
- `KZ_RomulC` — торжественный сериф, фактически «лицо» казахских пригласительных
- `KZOptima` — основной текст
- `KZPFMonumentaPro-Regular` — лэйблы/даты

Они **специально нарисованы** под казахскую кириллицу (Ә, Ө, Ұ, Ү, Қ, Ғ, Ң, І, Һ правильно сидят, не тянутся). Это огромная разница с Google Fonts, где Ә/Ө часто криво отрисованы.

**Плюсы этой модели:**
- Дизайнер может в Figma/Tyrasoft творить что угодно — каждый слой абсолютно позиционирован. Никаких «рамок компонентной системы».
- Результат визуально «вау» — 17 декор-изображений + 8 Lottie в одном приглашении.
- 500+ шаблонов на рынке → каталожное преимущество давит.
- Быстро для дизайнера: накидал слои, не думаешь о вёрстке.

**Минусы:**
- **Не responsive-first** — это 5700px absolute container, на других экранах через scale/overflow. На 390px смотрится идеально; на планшете/десктопе — пустые поля или масштабирование.
- **Слоёность = тяжело поддерживать**: правка шаблона = ручное двигание 50 элементов.
- **Vendor lock**: вы не владеете движком; если Tyrasoft поднимет цены или закроется — весь каталог теряется.
- **Quick-edit жёстко ограничен**: пользователь не может скрыть/поменять блок, только подставить текст в пред-слоты.
- **8 Lottie на страницу** — это вес, дёрганье на слабых телефонах, батарея.
- **Оплата вручную** через WA-менеджера (из их pricing-страницы) — нет нормального Kaspi API.

**Цены:** 4 900 ₸/мес за 1 сайт, 7 900 ₸/мес за 50 сайтов, 19 000 ₸/мес безлимит с API и личным менеджером. То есть для организаторов тоев это подписка, а не разовая покупка шаблона.

### 1.2 toi.com.kz — HTML-пайплайн с data-атрибутами

**Инженерная суть:** из реверс-инжиниринга (`temp_toi_template23.js`, `temp_toi_index.js`, ADR-доки вашего же репо, код `HtmlTemplateRenderer`):

Каждый шаблон — это **статический HTML-файл + папка ассетов**:
```
template-assets/uzatu-template23/
├── hero.webm + hero-poster.webp
├── frame-greeting.webp, frame-date.webp
├── countdown-bg.webp, confetti-l.webp, confetti-r.webp
├── divider-rose.webp, divider-hero.webp, divider-card.webp
├── dress.webp
└── ...
template-html/uzatu-template23.html
```

В HTML размечены специальные атрибуты:
```html
<h1 data-edit-id="hero-name" data-kk="Дана" data-ru="Дана">Дана</h1>
<section data-edit-container data-edit-id="sec-1">...</section>
<div data-bind="date" data-fmt-kk="YYYY ж. D MMMM">...</div>
<a data-bind="map" data-edit-id="map-label">...</a>
```

Редактор (`/invite/new-live`) работает так:
1. Загружает HTML в **изолированный iframe**.
2. **Парсит DOM** на предмет `data-edit-id` — строит форму редактирования с полями по атрибутам.
3. При вводе пользователя — модифицирует textContent нод с этим `data-edit-id` в iframe.
4. `data-bind="countdown|date|map|gallery|music"` — это виджеты, код которых инжектится в iframe.
5. `data-kk` / `data-ru` хранят дефолты для языков.

**На гостевой `/i/...` странице** (после публикации) — отдаётся уже «заполненный» HTML + виджеты. Никакого React там, vanilla JS.

**Шрифты toi** (из репо `temp_toi_template23.js` @font-face):
- `T23Script` = **Asylbek Shelley** — скриптовый казахский шрифт (почерк), имена в hero
- `T23Cer` = **Ceremonious** — церемониальный, подзаголовки
- Cormorant Garamond — основной
- Montserrat — лэйблы
- **`unicode-range` прописан явно**: U+0400–04FF, U+0460–052F (cyrillic-ext — казахские буквы). Значит, они специально собрали сабсеты с Ә/Ө/Ұ/Ң.

**Ассеты на шаблон** (template23): 15+ webp + 1 webm. Имена файлов у них **одинаковые по всем шаблонам** (frame-greeting, frame-date, divider-rose, confetti-l/r, hero-poster, etc) — видимо, это шаблон-паттерн, в который дизайнер подставляет свою графику.

**Категории шаблонов на текущий момент (2026-07-27):**
- wedding 27, uzatu 21, sundet 12, tusaukeser 10, merei 17, besik 10, tugankun 6, as 4, corporate 1, gender-reveal 2, syrga-salu 5
- **Итого: 117 шаблонов** в каталоге.
- Цены: free (watermark, 20 гостей), standard 2 990 ₸, premium 4 990 ₸, VIP 5 990 ₸, безлимит 10 000 ₸/мес.

**Плюсы HTML-пайплайна toi:**
- **Максимально быстро каталогизируется**: новый дизайн = один HTML-файл + папка с png/webp. Не нужно писать TS/React.
- Дизайнер/вёрстальщик может работать в привычных инструментах (Figma → экспорт HTML/CSS) или сразу верстать в HTML/CSS.
- **Каждый шаблон уникальный** — своя сетка, свои блоки, своя композиция. Это даёт вау-эффект.
- Гостевая страница лёгкая, без React-бандла — чистый HTML + виджеты.
- Редактор «из коробки» даёт WYSIWYG через iframe.

**Минусы toi:**
- **Парсинг HTML через regex/selectors хрупок** — ваш `HtmlTemplateRenderer.tsx` (spike) тоже это демонстрирует:
  ```ts
  const regex = new RegExp(`(<[^>]*${attr}[^>]*>)([^<]*)(</[^>]+>)`, 'g');
  ```
  Если вёрстка сложнее (вложенные теги внутри блока, например `<span>` для акцента), замена ломается.
- **Нет нормального контракта между дизайнером и разработчиком** — `data-edit-id` надо размечать вручную, опечатки не ловятся типизацией.
- **Дублирование виджетов** в HTML vs если потом нужно добавить новый виджет (например, seating) — нужно пройти по 117 файлам.
- **Оплата через чек-скриншот** (по их FAQ: «чек скриншотын жүктейсіз. Біз тексергеннен кейін шақыртуды белсендіреміз») — это **человек в цикле**, масштабируется плохо, нет антифрода на уровне API.
- **Судя по отсутствию API и видимой клиентской логики**, гостевые токены, реакции, расадка, экспорты CSV, напоминания не реализованы на том же уровне, что у вас.
- **Безопасность** iframe sandboxing хороша, но при полной кастомизации HTML нужен жёсткий санитайзинг; их визуальный редактор рискует XSS, если не чистить.

### 1.3 QazShaqyru — React-секции + TemplateManifest контракт

**Инженерная суть:** выбранная архитектура зафиксирована в `docs/architecture/ADR-001-invitation-editor-foundation.md` и `docs/templates/HOW-TO-ADD-A-TEMPLATE.md`:

1. **Шаблон = TypeScript-файл манифеста** (`src/lib/templates/manifests/<slug>.ts`), описывающий:
   - `renderEngine: 'react-sections'` (пока единственный прод-рендер)
   - `sections[]` — массив секций с `{ id, type, fieldBindings, props, defaultVisible, canHide, canReorder }`
   - `fields[]` — редактируемые поля `{ key, type, required, labelRu, labelKz, defaultRu, defaultKz, profiles }`
   - `theme` — accent/textLight/textDark/fonts (CSS-кастомные свойства)
   - `assets` — карта с именем → относительный путь (webp/png/webm)
2. **15 типов секций** (`src/components/invitation-layouts/sections/`):
   `envelope-intro, hero-names, body-invitation, cover-photo, calendar, countdown, venue-map, dress-code, gallery, final-text, rsvp, wishes, music, kaspi, program`.
3. **Один рендер** `SectionRenderer.tsx` для двух сценариев:
   - Гостевая страница `/i/[slug]`
   - Live Editor (режим редактирования добавляет `EditableField`, тап-по-полю)
4. **Документ-модель** `InvitationDocument` (`schemaVersion: 1`) — единая каноническая форма; форма-визард и быстрые поля только **инициализируют** документ, но не являются source of truth. Состояние секций (скрыть/порядок) хранится в `templateData.__documentState`.
5. **Шрифты** — self-hosted woff2:
   - `KZ Cormorant` (body serif) — кириллица/латиница/cyrillic-ext разными woff2
   - `KZ Montserrat` (лэйблы sans)
   - `KZ Marck` (script display, имитация почерка)
   - `KZ Unbounded` (ceremonial labels, premium)
   - CSS-кастомные свойства `--inv-font-body/display/ceremonial/label` переключаются через класс `.inv-manifest--wedding-luxury`
6. **Ассеты**: на данный момент `wedding-luxury` — **32 файла**, частично сгенерированных через `generate_assets.py` (FLUX.1-schnell через Hugging Face Inference API) в папках `backgrounds/, dividers/, hero/, ornaments/, overlays/`.

**Плюсы вашей модели:**
- **Типобезопасность**: TypeScript + Zod (`map-manifest-to-invitation.ts`, `template-data-schema.ts`) ловит ошибки на этапе сборки, а не в проде.
- **Один рендер = нет рассинхрона** «что вижу в редакторе vs что видит гость». У toi и shaqyru24 это решается разными путями (iframe в iframe; absolute-координаты → тот же canvas).
- **Секции — обогащаемый продукт**: добавили `ProgramSection` или `SeatingTable` — доступно всем шаблонам сразу. Не нужно править 117 HTML-файлов.
- **Бэкенд — это ваше главное оружие**:
  - **Kaspi API/webhook** с idempotency (не ручная проверка чеков)
  - **HMAC guest tokens** — токены гостей никогда не хранятся plaintext в БД; только `tokenHash`
  - **Family preview tokens** с той же моделью хэшей
  - **Restaurant share links** для тойхана (магия, которой точно нет у конкурентов)
  - **Seating** (рассадка по столам)
  - **Wish reactions** с fingerprint-анти-спам
  - **Kaspi gifts** (честная система переводов мимо сервиса)
  - **Guest funnel / reminders / CSV export / headcount / household labels**
  - **Open RSVP** (с хонипотом и капчей)
  - **Rate limiting**, bcrypt OTP
- **Живой редактор** (Live Editor) с тап-по-полю = современно, как в Canva/Telegram-premium. Форм-фактор «телефон-справа + панели снизу» — под мобайл эргономично.
- **Документ-состояние** позволяет скрывать/менять секции — у shaqyru24 quick-edit этого нет.
- **Agency/unlimited** тариф и менеджмент-ордера (`OrderType.managed`) — заложены в схему, значит можно делать «сделаем за вас».
- **SEO + i18n** на уровне: SSR страниц, md-блог на двух языках, карточки городов (almaty/astana), категории тоев (wedding/uzatu/sundet/...), OG-генератор, sitemap.
- **Тесты и CI-дружба**: Vitest unit (есть `__tests__` почти во всех папках `lib/`), Playwright e2e (свой `playwright.config.ts`), `check:env` скрипт, проверка переменных перед деплоем.

**Минусы вашей модели (говорим как есть):**
1. **Каталог — 1 шаблон** против 117 у toi и 500+ у shaqyru24. Причём сам `wedding-luxury` в комментарии к конфигу описан как *«temporary catalog bridge (not a quality baseline)»* и *«procedural placeholders»*. Генеративные ассеты через FLUX не тянут на «вау» визуал рядом с декором студийных дизайнеров.
2. **Один набор секций = потолок визуальной уникальности.** Пока вы верстаете всё через 15 React-компонентов, дизайнер ограничен тем, как эти секции выглядят. У toi каждый шаблон имеет собственный HTML — уникальная композиция гарантирована. У shaqyru24 — свободный canvas. У вас дизайн-решение шаблона = цветовая схема + другие декор-картинки + порядок/скрытие секций. Это очень сильно ограничивает «вау».
3. **Шрифты — не те, что ждёт локальный пользователь.** KZ_RomulC и KZOptima у shaqyru24, Asylbek Shelley и Ceremonious у toi — это узнаваемые в RK шрифты для тоев. У вас Cormorant + Marck Script + Unbounded — это красивые международные шрифты, но нет «казахского почерка». Без этого даже технически безупречное приглашение воспринимается как «обычный западный wedding evite», а не «той».
4. **Анимации скудны.** CSS `tpl-motion-luxe` ≠ 8 Lottie и hero.webm с конвертом. Вы осознанно отказались от Lottie (ADR и комменты), но это сказывается на первом впечатлении.
5. **HtmlTemplateRenderer — только spike.** Код есть (`lib/templates/html-template-renderer.tsx`, 191 строка), но он:
   - не работает в проде (нет шаблонов в `/template-html/` и `/template-assets/` — они отсутствуют в public)
   - regex-замена текста хрупка
   - не решён вопрос sandboxing и postMessage-протокола
   - не привязан к document-модели
   То есть вы написали «заглушку на будущее», но это не второй прод-рендер.
6. **Наследие quick-edit/EditorLayout/DraftEditorLayout** в репо осталось (4646 строк в `components/editor/`), но депрекейте: редирект с `/invitations/quick` на Live Editor, а само меню тулбара содержит кучу панелей (Kaspi, Guests, Seating, Gallery, Background, TextPresets, AI Fill, InviteHub, Social), которые в Live Editor разбросаны по bottom sheets. Риск «путаницы двух редакторов» пока не закрыт — код EditorLayout всё ещё импортируется где-то? Надо проверять; если да — это двойная поддержка.
7. **AI-fill и прочие «фичи ради фич»** (`lib/ai/apply-ai-fill.ts`, `fill-invitation.ts`) — без правильно построенной модели контента это может генерировать шаблонные неказские тексты. Опасно.
8. **Размер CSS приглашений** — `invitation.css` = 2318 строк, 239 `.inv-` селекторов. Это сопоставимо с одним большим HTML-шаблоном toi, но вы распределяете эти стили на 1 потенциальный шаблон (пока). При разрастании секций может стать неуправляемым.
9. **Нет встроенного видео-героя в проде.** В `wedding-luxury.ts` манифест имеет поле `heroVideo`, но в ассетах нет webm, только `hero-poster.webp`, `hero-01.webp`, `hero-02.webp`. `HeroNamesSection` это поддерживает технически, но не контентом.
10. **Lottie нет осознанно**, но минимальная 1–2 анимации на шаблон (конверт при открытии, конфетти) сильно бы подняли «wow» без урона производительности.
11. **Нет фото-подложки от пользователя в hero** как у конкурентов (isPhoto слой у Tyrasoft, cover у toi) — есть `coverPhoto`, но это отдельная секция; в hero вы используете студийный bgCover.

## 2. Как устроен редактор — детальный разбор

### 2.1 shaqyru24 — Quick-edit форма (форма-источник правды)

- Роут `/[lang]/quick-edit?page_id=…&site_id=…`
- SSR возвращает только язык; данные форм и page JSON грузятся **client-side** через API Tyrasoft.
- Форма сверху/слева, preview справа/снизу. Preview — это, по сути, тот же canvas, только с подставленными значениями.
- Пользователь не двигает слои, не меняет layout. Он только вводит: имя жениха/невесты, дату, место, адрес, текст приглашения, host names.
- На мобильных форма вертикально-последовательная, preview sticky-сверху.

**Слабость**: любое добавление поля = изменение у Tyrasoft и пересборка шаблона. Сильной кастомизации у пользователя нет.

**Сила**: UX проверен на 10 000+ клиентов (лендинг), 5 минут на создание.

### 2.2 toi.com.kz — Live editor через iframe + data-атрибуты

- Роут `/invite/new-live?template=category/templateN.html`
- Предварительный экран «Жүктелуде…» загружает JS и HTML шаблона.
- **Редактор = скан DOM**:
  - обходит HTML в iframe, находит все `[data-edit-id]`
  - строит панель полей: типы текста, фото, даты, карта привязаны к `data-bind`
  - при вводе — мгновенно правит textContent/атрибуты src внутри iframe
- **Живой preview — iframe буквально с тем же HTML**, что пойдёт на гостевую. Нет рассинхрона.
- **Мобильно**: форма внизу листается, preview сверху как айфон-мокап.
- При переключении шаблонов просто меняется `?template=…` — подгружается новый HTML.
- `data-kk`/`data-ru` позволяют хранить двуязычные дефолты.

**Плюсы:**
- WYSIWYG в чистом виде — что в iframe, то и у гостя.
- Простой механизм расширения полей — дизайнер размечает в HTML, редактор сам подхватывает.
- Гостевая лёгкая (без реакта).

**Минусы:**
- Завязка на DOM-парсинг и replace — если шаблон сложный (вложенные теги, списки), механизм хрупок.
- Нет типизации — опечатка в `data-edit-id` не отловится.
- Сложно добавлять кросс-секционные фичи типа «переставить блок», «скрыть блок», «перекрасить акцент» глобально.
- Редактор сам не может подсказать про заполненность шагов/валидность в отрыве от DOM.

### 2.3 QazShaqyru — Live Editor с документ-моделью

Текущая редакция кода (ветка `arena/019fa2ee-qazshaqyru`):

- `/invitations/quick` редиректит на **Live Editor** (`liveEditorHref`)
- `LiveEditorPage.tsx` (776 строк) — главный компонент, использует:
  - `useInvitationEditorStore` (Zustand-подобный свой стор, `lib/invitations/editor-store.ts`)
  - `InvitationDocument` как каноническое состояние
  - `localDraft` в `draft-storage.ts` с автосинхронизацией на сервер (`draft-sync-client.ts`)
  - 3 шторки (bottom sheets): **Fields**, **Sections**, **Inspector**
  - Нижняя навигация для мобайл (`LiveEditorBottomNav`)
  - `LiveEditorGuidedStart` — онбординг с шагами (basics/design/guests/publish)
  - `LiveEditorPublishConfidence` — индикация готовности (не просто «оплатите», а «что ещё заполнить»)
  - `resolveTapEditTarget` (`lib/live-editor/tap-edit.ts`) — клик по полю в превью → фокус на поле в форме
  - `LiveEditorPhonePreview` — превью в девайс-фрейме
  - `EditableField` в секциях — позволяет прямо в превью кликнуть на текст и редактировать
- **Create без регистрации**: draft хранится в localStorage, при появлении логина синхронизируется.
- **Guest flow** фичи интегрированы прямо в редактор: GuestsPanel, SeatingPanel, KaspiPanel, GalleryPanel, SocialPanel, PostPublishShare.

**Плюсы вашего редактора:**
- **Архитектурно самая проработанная модель** из трёх (document-schema с версиями, стор, автосохранение).
- **Тап по тексту** — современный UX (как Canva/Figma), лучше чем «форма отдельно → превью отдельно».
- **Guided mode** (пошаговый) помогает растерявшимся пользователям.
- **Конфиденс-полоса готовности** («до публикации не хватает даты/места») — у конкурентов такого нет.
- **Есть семейный preview** (familyToken) — можно показать черновик родителям до оплаты.
- **Секции можно скрывать/переупорядочивать** через `documentState` — у shaqyru24 и toi в базовом тарифе такого нет.
- **Поддержка локального черновика без регистрации** снижает отвал.
- **AI-fill** встроен, хотя и спорный по качеству.

**Минусы редактора:**
- **Кодовая база редактора большая**: 2177 строк в live-editor + 4646 в editor (legacy) + InvitationLayoutRouter с кучей пропов (140+ строк проп-интерфейс). Многовато для проекта на ранней стадии — риск энтропии.
- **«Два редактора»**: `live-editor/*` и `editor/*` — есть чёткое разделение (legacy vs новый), но надо следить, чтобы EditorToolbar/DraftEditorLayout не импортировались в LiveEditor как обязательная часть. При беглом просмотре LayoutRouter рендерит EditorToolbar — похоже на смешение.
- **Нет полноценного WYSIWYG-iframe**: у вас React re-render при каждом изменении. Это почти WYSIWYG, но нет абсолютной гарантии, т.к. «редакторный» режим и «гостевой» разделяются флагами (`isEditing`). При большом количестве секций может замедляться на слабых телефонах.
- **Не видно drag-and-drop перестановки секций** в мобильном интерфейсе (функция `canReorder` в манифесте есть, но UI для этого на мобайле ограничен стрелками/кнопками).
- **Фотогалерея / фоновое фото** — механизм UploadButton есть, но S3/R2-хранилище в env требуется; у пользователя без настройки хранилища всё упадёт. Надо убедиться, что есть внятная ошибка.

## 4. Какой способ лучше — честный вердикт по слоям

Нельзя ответить «мы лучше» или «они лучше» в одном абзаце. Ответ зависит от слоя продукта:

### 4.1. Сам рендер пригласительного у гостя

| Подход | Оценка |
|---|---|
| **Tyrasoft absolute canvas** (shaqyru24) | Визуально 5/5, архитектура 2/5. Хорошо для «wow-эффекта сейчас», плохо для масштабирования и responsive. Vendor lock. |
| **HTML + data-edit-id в iframe** (toi) | Визуально 5/5, архитектура 3.5/5. Лучший компромисс «скорость производства дизайнером / WYSIWYG / вес страницы». Минус — хрупкость DOM-парсинга и необходимость ручной разметки. |
| **React-sections + Manifest** (вы) | Визуально 2/5 сейчас (из-за 1 шаблона и генеренных ассетов), архитектура 4.5/5. Самый инженерно-правильный и самый масштабируемый в долгую (типизация, один рендер, обогащение секций), **но визуальный потолок ограничен 15 секциями**. Это архитектурный компромисс — вы платите скоростью каталожного разрастания за стабильность и фичи-богатство. |

**Рекомендация (не враг, не халтурю):**
Краткосрочно (ближайшие 2–3 месяца, пока каталог меньше 10–15 шаблонов) — ваш **react-sections** подход НЕ даст визуального паритета. Чтобы догнать по визуалу, вам **надо параллельно** ввести HTML-renderEngine в прод как равноправный путь рендеринга, а не как спайк. Вот почему:
- 15 секций с CSS-темизацией не заменят уникальную композицию (кривые рамки, нестандартную типографику, смещения, наложения фото на текст).
- Скорость выхода шаблонов у toi (HTML) — 1–3 дня дизайнеру на шаблон; у вас на react-sections это 5–7 дней с разработчиком, который правит секции под конкретный дизайн.
- Гостевой странице не нужен React; HTML с виджетами легче и быстрее на 3G/KZ-сетях.

При этом **не отказывайтесь от react-sections** — они остаются для:
- Flagship/premium-шаблонов с максимальной кастомизацией
- Функционала, который сложно наращивать в HTML (seating, per-guest токены/программа/рассадка)
- Будущих фич, которые внедряются у всех шаблонов сразу

### 4.2. Редактор

| Подход | Оценка |
|---|---|
| **Tyrasoft quick-edit** | 3/5. Работает, но пользователь залёг в форме, нет гибкости. |
| **toi iframe + data-edit-id** | 4/5. Простой, надёжный WYSIWYG, не тупит; но нет типобезопасности и продвинутых фич. |
| **Ваш Live Editor с документом** | 4/5 по архитектуре, 3/5 по текущей UX-готовности. У вас самая амбициозная модель (тап-редактирование, документ с версиями, локальный черновик, guided flow, конфиденс-бар, реактивные секции). Но 2177+4646 строк в редакторных компонентах при отсутствующем каталоге — это риск переинжиниринга. |

**Рекомендация:** Live Editor в вашей модели — правильный выбор. Перед тем как добавлять новые фичи типа AI, в первую очередь допилить визуальную полировку:
- Тап-редактирование должно ощущаться как Canva (мгновенный фокус, плавающая панель с жирностью/размером — пока есть только `LiveEditorTextTools`, проверь степень готовности)
- Убрать зависимость от legacy `editor/*` панелей или слить их с live-editor'ом
- Убедиться что drag-and-drop секций работает на мобильном (стрелки вверх/вниз допустимы, но drag приятнее)

### 4.3. Бэкенд и оплата

Здесь **ваш способ лучше всех** — без всяких оговорок:

- ✅ Kaspi API/webhook + idempotency + signature validation → у toi ручная загрузка скриншота, у shaqyru24 менеджер в WA
- ✅ HMAC guest tokens (hash-only в БД) → у конкурентов, судя по их URL, простые ID/slug без разграничения доступа
- ✅ Seating, household labels, CSV export для организаторов → нет ни у кого
- ✅ Restaurant share links для тойханы → уникальная фича
- ✅ Rate limiting, bcrypt OTP, honeypot/captcha на RSVP → наверняка у конкурентов слабее
- ✅ Order reconciliation webhook events ledger → промышленный уровень
- ✅ Agency тариф (9990/мес безлимит) с user-level планом → готовая B2B-модель

Это то, что вы **не должны ломать** ни при каких переделках шаблонной системы. Это ваше долгосрочное преимущество: у конкурентов бэкенд — «собрали форму и кнопку оплатить», у вас — полноценная SaaS-платформа для организаторов.

## 5. Что конкретно «как надо» vs «и так сойдёт» — честный диагноз по вашему проекту

### ✅ Сделано «как надо» (добротно, не переделывать)

1. **Продуманная БД** (Prisma-схема на 16 моделей, индексы, enum'ы, эвристики гостевого поведения).
2. **Безопасность** (HMAC токены, bcrypt OTP, rate-limit, captcha, honeypot, webhook dedupe).
3. **Платежи через Kaspi API**, а не «пришлите чек в WA».
4. **Единый документ-рендер** между редактором и гостем (уменьшает баги «в редакторе красиво, у гостя сломано»).
5. **Полная двуязычность** (middleware, server-side cookies, переводы в TS, labels в манифестах).
6. **Self-hosted шрифты** с woff2 и unicode-range (технически верно, надо только заменить набор шрифтов).
7. **Маркетинговая SEO-основа** (блог, страницы городов, категории тоев, OG, sitemap).
8. **Playwright e2e + Vitest unit** — зрелая практика.
9. **Docker Compose + Caddy деплой** — работает на VPS без магии.
10. **Agency тариф, managed orders, restaurant links** — задел на B2B и агентский рынок, которого нет у конкурентов.
11. **Template Manifest как контракт** + ADR-доки — это правильная инженерная культура.

### ⚠️ Сделано «и так сойдёт» / пока каркас (требует внимания, но не сломано)

1. **Каталог из 1 шаблона** при 117 у toi и 500+ у shaqyru24 — это не техническая проблема, а продуктовая реальность. Каталог пока, по сути, заглушка.
2. **Визуал wedding-luxury** — сам `catalog.ts` пишет «temporary bridge (not a quality baseline)», и ADR ругает generative placeholders.
3. **Шрифтовой набор** не даёт «тойного» ощущения. Marck Script вместо настоящего казахского скрипта.
4. **HtmlTemplateRenderer** — спайк из 191 строки, не в проде; архитектура готова, но не задействована.
5. **Наследие editor/* (4646 строк)** есть и, кажется, рендерится в LayoutRouter; нужно убедиться, что QuickEdit и DraftEditor не мёртвый код, который тянет вес и ментальную нагрузку.
6. **AI-fill** — лучше убрать из маркетинга до тех пор, пока тексты действительно получаются аутентичными и с казахским колоритом, а не универсально-европейскими.
7. **Lighthouse/производительность секций на слабых телефонах** — не проверял, но 2318 строк invitation.css + 15 секций + motion могут быть тяжелы на старых Android в регионах.

### ❌ Чего не хватает до «добротно»

1. **Второго renderEngine (HTML/iframe) как промышленного способа выпускать шаблоны пачками**. Без React-only путь к 50+ шаблонам — это 6–12 месяцев работы разработчика вместо 2–3 месяцев работы дизайнера.
2. **Казахского display-шрифта** в палитре.
3. **Минимум 10–15 готовых качественных шаблонов** в каталоге перед активным маркетингом — сейчас маркетинг (блог, SEO-страницы) опережает продукт.
4. **Галереи в реальном прод-шаблоне** (GallerySection есть, но ни один шаблон не использует 4 фото по-настоящему с пользовательскими загрузками через S3/R2).
5. **Video-hero (webm) в прод-шаблоне** — у обоих конкурентов видео-герой есть.
6. **1–2 аккуратные Lottie-анимации** (конверт открывается при первом входе / лёгкий конфетти) с уважением к `prefers-reduced-motion`. 8 не надо.
7. **Уверенности в S3/R2 uplodade для пользовательских фото** (фото пары, галерея) — без этого весь фотопайплайн не проверен.
8. **Удаления/отключения неиспользуемых редакторных панелей** во избежание поддержки двух параллельных UX.

### Лаконичный вердикт для вас:

**Ваш фундамент (бэкенд, безопасность, редактор-документ, SEO-деплой) — лучший из трёх.** Это реально добротно сделано, это скелет под серьёзный продукт, а не «и так сойдёт».

**Ваш главный долг — визуал и каталог шаблонов, и он архитектурно упирается в то, что вы выбрали react-sections как единственный прод-renderEngine.** Этот выбор даёт инженерную стройность, но не даёт дизайнеру свободы для вау-эффекта и скорости каталога. Оптимальный путь, который рекомендует и ваша же ADR — **включить HTML-renderEngine на равных правах с react-sections**, сохранив текущий бэкенд и document-модель. Тогда вы получаете:

- дизайнеры выпускают 50+ шаблонов в HTML-стиле как toi (скорость каталога)
- react-sections остаются для премиальных/функционально-богатых шаблонов (с seating/program/персональными токенами)
- общий бэкенд Kaspi/RSVP/seating/guests продолжает быть преимуществом
- визуальный паритет достигается за 2–3 месяца, а не за полгода

Если оставить всё как есть (только react-sections, один набор секций, AI-генерённые ассеты) — вы рискуете технически совершенный продукт, который **визуально проигрывает** даже при лучшем бэкенде. Как справедливо написал предыдущий агент: *«Backend у нас сильнее — но это не продаёт, пока визуал и каталог проигрывают.»* Пользователь платит 2990–4990 ₸ за ощущение праздника, а не за HMAC-токены.

**И последнее, без ложной патоки:** тот факт, что у вас есть ADR, тесты, план-каталог, документ-состояние, контроль чек-листа запуска (`check:env`), регламент добавления шаблона — это **сильная инженерная культура**, которой у конкурентов, похоже, нет. Это та самая «добротность», которую не видно с первого взгляда, но которая спасёт проект при росте. Защищайте её — и одновременно инвестируйте в визуал так, как вы уже инвестировали в бэкенд.
